# ADR-0013: Wave 1 Exit Surfaces - Settings, Output Styles, First Session, Compliance Parity, Overlap, and Routing Enforcement

**TL;DR:** This ADR closes roadmap rows 1.8 and 1.10, the last two rows of Wave 1. Seven decisions ship together. A per-project settings file (`.claude/nonfiction-studio.local.md`) lets an author tune gate strictness, thresholds, routing enforcement, and an output-style record, with warn-and-default corruption handling and a precedence rule that can raise gate strictness but can never un-coerce a judgment check. Two output styles (`manuscript`, `review`) ship as plugin components, offered once and never imposed, activated only through a namespaced settings value a live probe found is the only form the platform actually honors. `SessionStart` gains two fields, `initialUserMessage` (opening the studio dispatcher in a truly empty directory) and `reloadSkills` (picking up a generated project skill) - the second's same-session-liveness promise is adapted, not met, on probe evidence. Chat-surface compliance parity closes: a byte-identical verify-then-append stanza across the six agent-dispatching skills, checked by a new Tier A checker, plus a twelfth doctor check reporting an AI-use-log coverage fraction. A ninth CLI, `ns-overlap`, detects local n-gram overlap against an author's own research corpus, and its computation is shared verbatim with a new, seventh, warn-mode gate check. Agent dispatch itself now enforces model-tier and chain-edge routing, reading `agents/<slug>.md` frontmatter and `agents/_chain-permitted.yaml` directly rather than duplicating either into a new registry file. And the two shipped config templates are proven to carry the identical default check set, closing a template-divergence gap that turned out to be latent rather than live.

## Context

Wave 1's roadmap carried two remaining rows. Row 1.8 asked for three author-facing surfaces that had never shipped: a way to tune gate behavior per project without editing the shared config, a way to change how Claude's replies are shaped for drafting versus review work, and a first session that does not require an author to already know the right slash command. Row 1.10 asked for three trust surfaces: proof that a chat-only session (where hooks never fire) produces the same compliance trail a hook-backed session does, a way to catch an author accidentally echoing their own prior research into a new chapter, and enforcement - not just documentation - of the model-tier and chain-of-custody rules this plugin's own agents are supposed to follow.

Each of the seven decisions below answers one part of that list. None required a new file format invented from nothing; each reuses a pattern this plugin already established elsewhere - the walk-up directory search `findBookRoot` already performs, the warn-then-optionally-block double opt-in D-03 (layered Stop gate) already enforces, the shared-engine-module discipline S-07 (hooks and scripts) section 4 already requires, and the growth-policy test ADR-0009 (apparatus CLI) already wrote down for exactly this situation.

## Decision 1: a per-project settings file, with warn-and-default corruption handling and a never-un-coerce precedence rule

`.claude/nonfiction-studio.local.md` is a new, optional, per-project file: a YAML-frontmatter-fenced block followed by free Markdown "house notes" Claude reads at session start. `hooks/lib/settings.mjs`'s `loadSettings` walks up from the current directory the same way `findBookRoot` does, so the file is found from any subdirectory of a book project, not only its root.

Schema v1 carries four keys, each optional: `gate_mode` (`off`/`warn`/`block`, overriding `.studio/config.json`'s top-level `gate.mode`), `thresholds` (an object shallow-merged over `config.json`'s own thresholds, settings winning on a collision), `routing_enforce` (`off`/`warn`/`block`, read by Decision 6's dispatch guard), and `output_style` (a plain string recording Decision 2's offer outcome, not an activation switch). An unrecognized key is preserved unvalidated, so a later schema addition round-trips through an older reader.

**Corruption is warn-and-default, at two granularities.** A whole-file failure - unreadable, no frontmatter fence, the YAML dependency unavailable, invalid YAML, or frontmatter that parses to something other than a key/value map - returns empty settings and one collapsed-to-a-single-line warning sentence naming the file; nothing throws, and gate or hook behavior degrades to exactly the no-settings-file case. One YAML result is deliberately not treated as corruption: an empty or comments-only frontmatter block parses to `null`, routed to silent success rather than a warning, so a copy of the shipped example template with every key still commented out produces zero noise. A finer-grained failure - the file parses, but one or more *known* keys individually fail their own type or enum check - drops only the offending keys, keeps every surviving key (known or unknown), and names the dropped keys in a `droppedKeys` array alongside the warning. That array exists because Decision 6's dispatch guard needs to tell "the key I read was itself invalid" apart from "some other key was invalid, but mine was fine" - a single warning string cannot make that distinction, and Decision 6 below is the reason it was built.

**The precedence chain, and why it cannot be gamed.** `hooks/lib/gate-engine.mjs`'s `loadGateConfig` is the single choke point: `DEFAULT_GATE <- .studio/config.json (gate + thresholds) <- settings (gate_mode -> gate.mode; thresholds -> shallow merge) <- structural coercions` (D-03: `thesis_alignment` and `quote_fidelity` can never block in v1). The settings overlay runs before the coercion blocks, and settings can raise the top-level `gate.mode` all the way to `block` - but it can never promote either coerced check out of `warn`. This is not a convention that could be accidentally violated: the settings schema has no per-check mode key at all, so there is no field in it a settings file could set that the coercion blocks would need to override. The two layers simply do not share a write target - confirmed by mutation, not just by inspection. Literally reordering the overlay to run after the coercion blocks turns nothing red, precisely because the two write disjoint state: the overlay never touches `gate.checks` and the coercion blocks never touch `gate.mode` or `thresholds`, so the final config is byte-identical either ordering runs first. The mutation that does turn a test red is the actual bug this ordering guards against - the overlay additionally writing `gate_mode` into `gate.checks.quote_fidelity.mode` directly, run after the coercion blocks - which lets a coerced check reach `block` again. That combined mutation is what a reviewer should expect the ordering pin to catch, and it does.

`docs/formats/settings.md` is the normative page, matching `hooks/lib/settings.mjs` key-for-key, including every failure mode's exact `droppedKeys` behavior.

## Decision 2: output styles ship as plugin components, offered once, and consent widens the plugin's settings-write claim

`manuscript` and `review` ship under `output-styles/`, a new component class for this plugin: prose-first drafting responses with claim-marker discipline preserved, and terse verdict-first tabular responses for gate and status work, respectively. Neither is forced. `nfs-new-book` offers a consented choice once per project, gated on whether `output_style` (Decision 1) already carries a recorded answer, and reachable from every re-initialization path a project can be entered through, not only a fresh one.

A live platform probe decided the activation mechanism, and its finding is the load-bearing fact behind everything else in this decision: a plugin-shipped output style is discovered and loaded by the platform, but activating it requires writing the **namespaced** settings value `plugin-name:<frontmatter name>` - for this plugin, `nonfiction-studio:Manuscript` or `nonfiction-studio:Review`. Four candidate values were tried against a live headless session (a bare frontmatter name, a bare filename slug, the correctly namespaced form, and a namespaced-but-wrong-casing form); only the fully correct namespaced form activated the style, confirmed by the style's own marker appearing in the model's reply, and the three incorrect forms failed with no error of any kind on either side - a plugin author guessing at the wrong form has nothing to tell them they guessed wrong. The offer therefore composes and writes this exact value; it never asks an author to guess it. The two frontmatter fields governing forced activation were independently confirmed as real platform schema fields (`keep-coding-instructions`, defaulting off; `force-for-plugin`, which would activate a style on every session for every user of the plugin) and neither style sets `force-for-plugin`, which is what makes "never imposed" true rather than aspirational.

**The write claim widens, deliberately and narrowly.** ADR-0008 (status HUD) established that exactly one code path in this plugin could ever write a user's own settings - the `doctor` skill's consented, one-time `install-statusline` mode, writing `~/.claude/settings.json` at USER scope. That claim was, and remains, true of USER-scope settings specifically. This decision adds a second, narrower kind of consented write, at PROJECT scope: `nfs-new-book`'s output-style offer reads `.claude/settings.local.json` inside the author's own project (absent treated as `{}`, invalid JSON halts with nothing written), merges in the namespaced `outputStyle` value preserving every other key, states the exact JSON before asking, and writes only on an explicit yes - the identical "state exactly what will be written, and ask" shape `install-statusline` already uses. `doctor`'s `install-statusline` remains the only code path in this plugin that writes the **user's own** settings; this is a second, project-scoped write path for a different file, not an exception to that USER-scope claim. Declining, or the platform's own permission prompt for the write being denied, leaves the offer open for a later re-run rather than recording a false decline.

## Decision 3: `SessionStart` gains `initialUserMessage` and `reloadSkills`; same-session liveness is adapted, not met

Both fields are new, and both are nested under `hookSpecificOutput` - a live probe confirmed a top-level placement of either field is silently ignored by the platform, with no error on either side, the same "convincing-looking manifest entry that does nothing" failure mode ADR-0008 (status HUD) named for a plugin `settings.json`'s `statusLine` key.

`initialUserMessage` opens the studio dispatcher (`/nonfiction-studio:nfs-start`) unprompted, but only when no book project is found **and** the directory is truly empty - an allowlist check (`.claude`, `.git`, `.gitignore`, `.DS_Store`, `Thumbs.db`) rather than a bare emptiness test. This guard exists because "no book project found" alone fires in every unrelated directory that happens to have this plugin installed at user scope; without it, opening the dispatcher unprompted would hijack the first turn of a project this plugin has nothing to do with. The field's effect was confirmed live in headless mode: it becomes a genuine first user turn in the session, with its own model response, before whatever the author actually types.

`reloadSkills` fires when a book project is found and a generated `book-context` skill already exists for it - a project-committed quick-reference (thesis one-liner, top style rules, chapter map, open-claims count) `nfs-new-book` writes only on the author's explicit consent, documented in `docs/privacy.md`. **Here the probe evidence forces an honest downgrade of the original acceptance language.** `reloadSkills: true` affects only the platform's own skill-scan step at the moment `SessionStart` runs; it does not grant same-session liveness to a skill file written mid-session, because the platform's skill scan has already completed by the time a mid-session write happens. A skill generated during a running session is not invocable in that same session regardless of this field. The confirmed recovery path is a session restart, or a session **resume**, which re-fires `SessionStart` end to end (including this same `reloadSkills` emission) and does pick up a skill written earlier in the resumed session's own history. **OPP-P12 (zero-friction first session)'s same-session-liveness clause is therefore recorded as ADAPTED, not met**: the generated skill's own body, the `nfs-new-book` consent question, and every reference page describing this feature state plainly that the skill becomes usable starting the next session (or a resume), never the current one. No document in this plugin claims same-session liveness for this feature.

## Decision 4: chat-surface compliance parity closes, with the coverage fraction on the doctor report

The six agent-dispatching skills (`nfs-capture-voice`, `nfs-draft`, `nfs-fact-check`, `nfs-interview`, `nfs-outline`, `nfs-research`) now carry a byte-identical "Compliance append (verify-then-append)" core: before a flow's writes, count the existing `ai-use-log.jsonl` records already targeting each file about to be touched; after the writes complete, re-count; if the count increased, a hook already logged the write on the current surface (`PostToolBatch`, which does not fire on chat) and the skill appends nothing further; only when the count did not increase does the skill append its own record. This closes the gap a chat-only session previously had - no hook, no compliance record - without duplicating a record a hook already wrote on a hook-backed surface. A new Tier A checker derives the dispatching-skill set from each skill's own frontmatter `chain:` list, never a hardcoded roster, and asserts the shared core is present and byte-identical everywhere it is supposed to be, so the six-way parity cannot rot silently as a seventh dispatching skill is added later.

`ns-doctor` gains a twelfth check: it reports, per chapter with any recorded write, whether a file's on-disk modification time postdates the newest `ai-use-log.jsonl` record naming it (an "uncovered writing window" notice), and always states the coverage fraction as a sentence ("`ai-use-log` covers N of M chapters with writes"). **The coverage fraction's placement is itself an acceptance adaptation, not an oversight**: OPP-P09 (chat compliance parity)'s original language anticipated the fraction surfacing on a dedicated disclosure-report skill, but that skill (and the `publish-readiness` skill that would consume it) is Phase 2, not yet shipped. The fraction lives on the doctor's report today, the only shipped consumer capable of hosting it, and will be inherited by the disclosure-report skill once that work is scheduled rather than duplicated into a second computation.

**A known property, disclosed rather than hidden**: the mtime heuristic behind "uncovered writing window" cannot distinguish a genuinely unlogged edit from an ordinary git checkout, which stamps every file with the checkout's own mtime regardless of when its content was actually last written. Measured directly against the committed sample book - whose two chapters both have on-disk mtimes from git's own checkout, postdating every one of their `ai-use-log.jsonl` records - the doctor correctly reports full coverage by presence ("covers 2 of 2 chapters with writes") alongside two "uncovered writing window" notices by recency, with the overall report still `status: valid` and exit 0 throughout. These are two independent facts, not a contradiction: covered-by-presence answers "did anything log this file," and uncovered-by-recency answers "did the file change more recently than the newest thing that logged it," and a fresh checkout can honestly be both. An uncovered window across a clone or checkout boundary is therefore a notice for an author to interpret, never a finding the doctor treats as proof of an actual compliance gap.

## Decision 5: `ns-overlap`, the ninth shipped CLI, sharing its computation with a new gate check

`ns-overlap` detects local n-gram overlap between chapter prose and an author's own research corpus - `research/packets/*.md`, every non-empty `verbatim` field in `research/evidence-log.md`, and, when present, `context/prior-work/*.md` - entirely offline, with no network access. Both the chapter text and every corpus text are normalized identically (Unicode NFC, case-fold, typographic-to-straight quote conversion, whitespace-run collapse) before an 8-word shingle comparison chains matching shingles into maximal spans; a merged span of at least 15 words (the shipped default, overridable via `thresholds.overlap_min_words` in `.studio/config.json` or the per-project settings file from Decision 1) is a finding naming both locations. A chapter span sitting inside a passage that is already properly quoted and anchored to a `[quote: EV-nnnn]` marker is excluded as already attributed - reusing the claims engine's own quoted-span-finding helper rather than a second implementation of the same grammar - and that exclusion is reported as an informational count, not dropped silently.

`overlap` registers as the seventh configurable gate check, warn-mode by default, calling `findOverlaps` and `discoverCorpora` directly from the same engine module `bin/ns-overlap` calls, so the CLI and the gate check can never compute overlap differently. Unlike `thesis_alignment` and `quote_fidelity`, this check is **not** structurally coerced: it is fully deterministic, so - per the same double opt-in D-03 (layered Stop gate) already requires of every other deterministic check - an author can raise it all the way to `block` on both the top-level `gate.mode` and this check's own mode. Measured against the committed sample book, the check produces zero findings, confirming no false positives against real, unremarkable prose.

**The D-05 (five shipped CLIs) growth-policy test, answered again.** ADR-0009 (apparatus CLI) set three questions a CLI candidate should answer yes to at least one of, before choosing the CLI shape over skill-only logic. `ns-overlap` answers yes to two: correctness is a deterministic, machine-checkable property (byte-identical `--json` output across two runs against unchanged input, and a fixture with a planted 30-word lift that a failing test can be written against before the feature exists), and two callers - the CLI and the gate check - need the identical computation, which is exactly the shared-engine-module discipline this plugin already uses to avoid drift between a CLI and its gate-check twin. D-05 grows from eight to nine: `ns-statusline` was the sixth (ADR-0008), `ns-notes` the seventh (ADR-0009), `ns-status` the eighth (ADR-0011), and `ns-overlap` is the ninth.

## Decision 6: routing enforced at dispatch, with no separate routing registry file

`hooks/pre-tool-use.mjs` gained a dispatch-time branch, firing when the event's `tool_name` is `Agent` or `Task` and the dispatch targets one of this plugin's own agents. It enforces two rules. The **model-tier rule** (D-18, in-plugin model routing): when a dispatch carries an explicit model override that disagrees with the target agent's own declared `model:` frontmatter (and that declaration names a tier rather than `inherit`), it warns citing both values. The **chain-edge rule**: `agents/_chain-permitted.yaml`, previously enforced only at lint time, is now also read at dispatch time; when the dispatching context is itself a plugin agent and the edge to the requested agent is not on that contract's list, it warns naming both agents.

**No separate routing registry file was built.** A design that recorded model-tier assignments in a new `_routing.yaml` (or equivalent) would duplicate what D-18 (in-plugin model routing) already declares once, in each agent's own frontmatter `model:` field - the single source of truth this decision reads on demand, at dispatch time, rather than caching or mirroring into a second file that could drift out of sync with the frontmatter it would be describing. `agents/_chain-permitted.yaml` already existed as the lint-time chain contract; this decision gives it a second reader, not a second file.

**Live-captured dispatch evidence decided the matching rule.** A platform probe confirmed the live `tool_name` value is `"Agent"` (`"Task"` is matched too, since the installed binary's own attribution helper still checks for it as a prior or parallel surface), and that a plugin agent's `tool_input.subagent_type` arrives **namespaced**, `plugin-name:agent-name`. The guard strips this plugin's own namespace prefix before comparing; an unnamespaced or foreign-namespace value exits silently before either rule runs, so a main-session dispatch or a dispatch to some other plugin's agent never triggers a false warning. A captured warn-mode dispatch, verbatim: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"Routing: line-editor declares model sonnet (D-18 in-plugin model routing); this dispatch requests opus."}}`.

Both the model comparison and the namespace guard are mutation-tested, not just exercised by a happy-path test. Inverting the model-tier equality check turns a named test red, confirming a matching model genuinely stays silent and a mismatched one genuinely warns rather than the reverse. Removing the namespace guard turns exactly one test red: without it, an unnamespaced dispatch target is compared against the chain contract as a literal `null`, which the contract naturally does not list, and the branch would warn "not a declared edge" on every ordinary main-session dispatch - the false positive the guard exists to prevent.

Both rules share one `routing_enforce` mode (Decision 1): `warn` (default, including an absent settings file) emits the caution without stopping the dispatch; `block` denies it with the identical sentence; `off` silences the whole branch before any file is read.

**The fail-open rule for a settings-file problem was revised once, on a live-reproduced gap, and this is the current, correct behavior.** The first version silenced this branch on *any* settings warning, of any kind. A live review reproduced a real failure this let through: a settings file carrying an unrelated, invalid `gate_mode: bogus` value beside a perfectly valid, explicitly configured `routing_enforce: block` produced empty output on a mismatched-model dispatch - a deliberately configured block control going silently dark because of an unrelated typo elsewhere in the same file. The rule was narrowed to three cases, keyed off the `droppedKeys` array Decision 1 describes: a whole-file parse failure stays silent (no key can be attributed); `routing_enforce` itself being the individually dropped key stays silent (that specific author intent is genuinely unknown); but a warning naming any *other* key does not silence the branch - the valid `routing_enforce` value governs exactly as if the unrelated invalid sibling were absent. "Advisory only" and "a configured `block` silently does nothing" are different failure classes, and only the narrower rule keeps a real deny reliable.

## Decision 7: config template parity, closing PF-28 (config template divergence)

`templates/config-defaults.json` and `templates/book-scaffold/.studio/config.json` are the two shipped starting points for a new book's `.studio/config.json`, and they had drifted: neither carried every check `DEFAULT_GATE.checks` (`hooks/lib/gate-engine.mjs`) declares as the actual default. Both templates now carry exactly the same `gate.checks` key set as `DEFAULT_GATE`, and a gate-suite test asserts both parsed templates' key sets deeply equal `Object.keys(DEFAULT_GATE.checks)`, so the two cannot silently diverge again as a future check is added.

**The behavioral question this divergence raised - did a book actually gate differently depending on which template it started from - has a definite answer: no.** `loadGateConfig` merges every template's raw `gate.checks` object with `DEFAULT_GATE.checks` on read, taking the default entry for any check name the raw config omits (`Object.assign({}, DEFAULT_GATE.checks[name], rawChecks[name] || {})` for every name in `DEFAULT_GATE.checks`, unconditionally). A book scaffolded from either template therefore received the identical effective check configuration at gate-run time regardless of which template's raw JSON was missing an entry; the templates' own text disagreed with each other, but the two paths this repository actually exercises did not. PF-28 (config template divergence) closes on that behavioral ruling: the gap was in the templates' own text, latent rather than live, and is now closed at both levels - the templates read alike, and a test guarantees they cannot drift apart again.

## Consequences

- **The doctor's `quote_fidelity` coercion notice gap, found while building Decision 1, is closed alongside it.** `hooks/lib/doctor-engine.mjs` reported a D-03 coercion notice for `thesis_alignment` but not its structural sibling `quote_fidelity`; both templates and the doctor engine now treat the two symmetrically.
- **A stale doc claim, found while building Decision 5's gate check, is corrected.** `docs/formats/gate-report.md` had claimed `ns-gate` writes back into `.studio/progress.json`'s `last_gate.report` field; `ns-gate` writes only under `.studio/gate/`, per D-06 (single-writer state discipline), and `progress.json`'s `last_gate` stays reserved and unpopulated in v1 - the same fact every other page describing this already stated correctly.
- **The close-out amendment set** (landed separately in the gitignored planning canon this ADR is written precisely enough to amend from, the same convention ADR-0008 (status HUD) and ADR-0009 (apparatus CLI) used for their own forward-pointing consequences): a settings file joins the roster of first-class plugin component classes; the output-styles component class, named as future work in ADR-0008, is complete, and the consented-write sentence widens per Decision 2; the `SessionStart` field names from Decision 3 join the existing context-continuity decision; the in-plugin model-routing decision (D-18) gains an enforcement clause describing dispatch-time behavior, not lint-time behavior alone; and the CLI roster's own record grows to nine.
- **Both roadmap rows this ADR closes carry one open item each, deliberately not addressed here.** Row 1.8's Cowork surface claim for the generated book-context skill stays under the standing Cowork caveat (ADR-0002), untested on that surface, same as everything else this plugin has not yet exercised there. Row 1.10's disclosure-report and `publish-readiness` skills remain Phase 2, unshipped; they inherit Decision 4's coverage fraction rather than recomputing it, once built.
- **This ADR authorizes no further code.** Every decision above is already implemented on this branch; this document records why each shape was chosen, not a plan for future work.
